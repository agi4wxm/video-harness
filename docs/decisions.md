# 决策记录

每条：决定 · 理由 · 代价。

## D1 · skill + CLI 为主，MCP 降为薄适配器
- **决定**：流程与规范写在 skill 里，所有行为实现在 `vh` CLI；MCP 只转发 `vh` 命令（截图以图片返回、长任务走 job）。
- **理由**：rea-video、auto-motion 等能跑通的同类项目都是这种形态；有 shell 的 agent 直接调用 CLI 最简单、最好调试；原先"server 内存里的状态机 + 闸门"设计过重，实现一直停在 v0。
- **代价**：没有 shell 的客户端只能用 MCP 的子集功能（工具已覆盖主流程）。

## D2 · 质量 = 硬约束 + 简报约定 + 看图复核；统计区间只做诊断
- **决定**：`vh check` 只做可客观判定的硬约束；审美靠简报（设计体系、语义色、母题、Banned）、复核（全新上下文，tasks / answers）和用户 A/B；`vh compare` 与参考分布比对，偏离只提示不拦截。
- **理由**：反面样本 battery-80 的统计指标全部落在参考区间内，看起来仍然廉价；质量来自设计体系、视觉想法、连续性和呼吸式节奏，这些不是区间能描述的。
- **代价**：审美判断依赖复核质量；用"全新上下文 + 固定题目 + 固定问题格式"降低偏差。

## D3 · 只用代码生成画面
- **决定**：不调用图片 / 视频生成 API。插画、角色、场景都用场景图（SVG）、Canvas、Three.js 画；真实 logo / 产品图只能用用户提供的文件。rea-video 判为 AI 视频 / 实拍的段落，复刻路线改写为代码路线或"需要用户提供素材"。
- **理由**：用户明确要求代码生成；代码画面可复现、可校验、可自动产生评测真值。
- **代价**：写实类画面做不了，需要用户提供素材。

## D4 · 统一的镜头约定：场景图优先，html / react 兜底
- **决定**：积木与 `local` 镜头返回场景图，由一个渲染器统一画；任意网页技术走 `html`（`window.__vh.seek(t)`，预渲染成视频）；Remotion 组件走 `react`。
- **理由**：场景图让渲染、版面校验、评测真值三处共用一份描述；html 约定覆盖 awesome-opus5-5-videos 里大量 Canvas / Three.js / GSAP 做法。
- **代价**：react 镜头没有场景图，版面校验跳过；场景图里的文字宽度是估算（±10%）。

## D5 · 节拍是分镜的基本单位，且必须先写视觉想法
- **决定**：分镜 v2 以节拍为一级结构（时间、旁白、idea、焦点、母题）；`idea` 必填；节拍表需用户确认后才能构建。
- **理由**：MG / 讲解视频的节奏单位是视觉节拍，不是硬切；"每个节拍画什么具体的东西"是创意的核心，必须在写代码之前完成。

## D6 · 默认横屏 16:9、ElevenLabs 配音
- **决定**：默认 1920×1080 @30；配音 ElevenLabs（`eleven_multilingual_v2`，逐句请求 + 精确停顿 + 响度规范化，内容哈希缓存）。
- **理由**：用户选择。逐句合成让停顿可控（插画科普约 44% 的画面变化落在停顿里），也让改一句只重合一句。
- **代价**：句间韵律连续性略弱，用 `previous_text` / `next_text` 缓解。

## D7 · 分析以 rea-video 为底座，只做它不做的部分
- **决定**：制作方式、包装层、声音分轨用 rea-video；`analyze/` 保留版式感知切镜、视觉节拍、旁白锚定、调色板、多片聚合，退役 OCR、响度、缓动拟合。
- **理由**：不重复造轮子；实测中 rea-video 在固定版式与 MG 长镜头上的问题，正是这几项能补上的。通用修复（版式感知、字幕判定）适合回馈上游。

## D8 · 评测真值来自自己的场景图
- **决定**：`vh eval synth` 随机生成分镜并渲染，真值（切点、转场、文字出现时刻）直接来自场景图；真实视频的人工标注作留出集，只验收不调参。
- **理由**：没有可靠真值，分析端的任何改进都无法证明有效。
